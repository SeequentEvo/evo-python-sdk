evo.compute.engine.ComputeClient

Instance-bound async entry point to the compute task catalogue.

Reach a task as client.<topic>.<task> and call await client.<topic>.<task>.run(...) to submit it and wait for its results. arun does the same for names held as strings.

Parameters:

Name Type Description Default
context IContext

An authenticated Evo context.

 required
cache_ttl_seconds float

How long a discovered task catalogue is cached.

 DEFAULT_CACHE_TTL_SECONDS
validate bool

Check the parameters against the task's JSON Schema before submitting (required-field presence, and, under deep_validation, known value constraints). Defaults to True. False turns off deep validation too, whatever deep_validation says. It does not make the call unchecked: the parameters are still bound to the task's required arguments, and explicit extra-field rules still apply. Custom runners also retain their own parameter checks.

 True
deep_validation bool

Additionally check the full JSON Schema Draft 2020-12 constraints. Defaults to False. Only consulted when validate is True.

 False
check_schemas bool | None

Check that each referenced geoscience object is of a schema the task declares support for. Defaults to following validate. Independent of it because the cost and the question differ: schema validation is local and free, while this loads each referenced object's metadata. Pass False to keep validation but skip the requests, or True alongside validate=False to keep the guard that catches an object the task cannot read.

 None
fb IFeedback

Feedback used while waiting for any job submitted by this client. Set it here so engine options do not occupy task parameter names in the namespace. TaskJob.results can override it for one wait.

 NoFeedback

arun async 

arun(
    topic: str,
    task: str,
    parameters: dict[str, Any],
    *,
    validate: bool | None = None,
    deep_validation: bool | None = None,
    check_schemas: bool | None = None,
) -> Any

Run a task by name, using its custom runner when one is registered.

Parameters use the same names as client.<topic>.<task>.run(...). Custom tasks return their native result; other tasks return TaskResult. Validation options override the client's settings for this call. Preview is off unless parameters explicitly includes preview=True. Feedback comes from the client; for one call, use :meth:asubmit and pass fb to job.results.

Submit by name, using the same custom runner as attribute-based submission.

Validation options have the same meaning as on arun. The accepted job carries its result converter and client feedback for the caller's eventual wait.
